# Windows_SC バージョン管理

更新日: 2026-08-15

現在のソースバージョンは`0.9.2`、GitHubで公開済みのタグ／配布版は
`v0.6.2-beta.1`である。ソースの版番号更新、ビルド成功、配布物の公開は
別の状態として扱う。`0.9.2`は配布前確認、成果物生成、タグ付けを終えるまで
公開済みとは記載しない。

次の配布版は内容と検証範囲で決める。

- 現在の修正を知人向けに配布する場合: `0.9.2`
- 正式版候補としてPhase 6の回帰確認へ進む場合: `1.0.0-rc.1`
- RCで重大な問題がなかった場合: `1.0.0`

正式版前のリファクタリングは挙動を変えない小規模な整理に限定し、設定形式、
スタート検出、モーション状態機械を大きく変更しない。

## 更新方法

リポジトリ直下の`Version.props`をアプリ版の正とする。

- `VersionPrefix`: ソースまたは配布候補のバージョン番号。`メジャー.マイナー.パッチ`形式とする。
- `VersionSuffix`: 開発・試験版では`dev`、`beta.N`、`rc.N`を使い、安定版番号では空にする。空であることだけでは公開済みを意味しない。

設定画面からコピーする環境情報には、この値が自動的に表示される。実行ファイルのアセンブリバージョンとファイルバージョンにも`VersionPrefix`が反映される。

版を変更するときは、数値4区切りの`Windows_SC/Package.appxmanifest`、
`CHANGELOG.md`、README、対象版を記載する現行`docs`、配布用READMEも同じ変更で
同期する。リポジトリ全体から旧版番号を検索し、履歴である`docs/archive`を除く
関連箇所を更新する。

利用者に影響する変更は、次のバージョンを公開するまで`CHANGELOG.md`の
「未リリース」へ追記する。公開時にその内容を新しいバージョン見出しへ移し、
公開日を記録する。実装途中の細かな変更はバージョン番号を上げず、Gitの
コミット履歴で追跡する。

## 番号の目安

- パッチ: 不具合修正だけを行った場合（例: `0.5.0` → `0.5.1`）
- マイナー: 後方互換性のある機能追加（例: `0.5.0` → `0.6.0`）
- メジャー: 設定互換性を壊す変更、または初回正式版等の製品上の大きな区切り

## 開発段階の接尾辞

- `dev`: 日常の開発・検証中
- `beta.1`, `beta.2`: 主な機能が揃い、複数環境で試験する版
- `rc.1`, `rc.2`: 正式版候補。原則として不具合修正だけを行う版
- 接尾辞なし: 正式に配布する安定版

番号はコミットごとではなく、配布物を作る区切りで更新する。同じバージョンの配布物を作り直す必要がある場合は、内容を判別できるよう最低でもパッチ番号を上げる。

初回正式候補では`VersionPrefix`を`1.0.0`、`VersionSuffix`を`rc.1`にする。
正式配布時は`VersionPrefix`を維持し、`VersionSuffix`を空にする。MSIXは公開
しないが、ビルド用メタデータとして数値4区切りが必要な
`Package.appxmanifest`の`Identity Version`も同じソース版へ合わせる。

## 配布形式との関係

- 現行の生成・検証対象はx64自己完結ZIPである。
- 単一EXEを再採用する場合も同じアプリ版を使い、ZIPと区別できる成果物名にする。
- MSIXは公開Releaseへ含めない。
- 同じ版番号の成果物を内容だけ差し替えない。
