# Windows_SC プロジェクトレビュー

レビュー日: 2026-09-05

対象ソースバージョン: `0.9.3`

対象コミット: `6948938`

対象範囲: 製品コード、Core、テスト、現行文書、配布スクリプト

## 1. 文書の目的

本書は、現行プロジェクトをバグ、設計、保守性、セキュリティ、プライバシー、
パフォーマンスの観点から確認した結果をまとめる。再現できた不具合と、コードの構造から
判断したリスクを区別し、修正の優先順位と確認方法を示す。

優先度は次の基準で付ける。

- `P1`: 配布判断の前に修正する。主要機能の失敗、起動不能、意図しない操作につながる問題。
- `P2`: 次の開発単位で修正する。データ保護、長時間安定性、プライバシー、性能に関わる問題。
- `P3`: P1、P2の修正後に段階的に進める保守性改善。

## 2. 総合評価

`Windows_SC.Core`へのUI非依存コードの分離、設定検証、保存時の一時ファイル利用、
通常ログと詳細ログの区別、COM解放順の文書化など、障害範囲を小さくする土台は整っている。
Debug／Release x64ビルドとCore自動テスト72件も成功している。

一方、コマンド実行、マクロからのキー入力、破損設定の復旧、アプリ別音量状態の保存には、
ビルドと現行テストでは検出できない実行時問題がある。特に最初の3件は主要機能の失敗や
継続的な起動不能につながるため、`0.9.3`の配布前に修正する。

### 2026-09-05の判断と対応

- P2-05の送信先固定は採用せず、ShortcutKeyは送信時点の前面ウィンドウへグローバル入力として送る。物理修飾キーも補正せず現行挙動を維持する。
- P2-02はアプリ単位の同一`SettingsPersistenceCoordinator`を共有し、終了時に保存完了を待つ方針で対応した。
- P1-03は旧版を移行し、破損・型不正を退避して既定値へ復旧する。将来版スキーマだけは上書きせず、警告して終了する方針で対応した。
- P2-01はアプリ別音量状態の保存全体を直列化し、`null`要素を破損として隔離する方針で対応した。
- P2-07はキュー上限5000件、連続同一失敗の集約、通常／詳細それぞれ4ファイル保持、スリープ／休止状態からの復帰時ローテーションで対応した。

上記はコードとCoreテストへ反映し、Coreテスト81件が成功した。GUI、スリープ／休止状態、ログ大量発生の実機確認は未確認である。

## 3. 優先度別の改善点

### P1-01 引用符を含むコマンドと、空白を含むbat／cmdパスを正しく実行できない

分類: バグ、互換性

確認状態: 再現済み

`ActionExecutionService`は`cmd.exe /d /s /c`へコマンド全文を`ArgumentList`の1要素として
渡している。これは.NET側の引数エスケープとcmd側の引用規則が重なり、引用符が意図した形で
解釈されない。レビュー用検証では、引用符付き`echo`に余分なバックスラッシュが入り、
空白を含むパスのcmdファイルは終了コード1になった。

影響:

- 引用符を含むCommandが別の内容として実行される。
- 空白を含むフォルダーにあるbat／cmdを起動できない。
- 引数、パイプ、リダイレクトを含む操作でも誤解釈が起きる可能性がある。

対象:

- `Windows_SC/Services/ActionExecutionService.cs`の`CreateCommandStartInfo`
- 同ファイルの`BuildCommandLine`、`BuildCommandScriptLine`

改善案:

1. cmdへ渡す最終文字列の引用規則を一箇所へ集約する。
2. CommandとBatchFileで必要な引用処理を分ける。
3. 空白パス、引用符付き引数、`&`、`|`、`>`、末尾バックスラッシュを含むケースを、
   実際の`cmd.exe`を起動する統合テストで確認する。
4. 登録内容は利用者が明示的に実行するコマンドであるため、任意コマンド実行という製品仕様は
   維持しつつ、文字列が意図どおりに渡ることを保証する。

### P1-02 待機後のマクロからUIスレッド外でウィンドウを操作する

分類: バグ、非同期設計

確認状態: スレッド境界を再現済み、実GUIは未確認

`MacroExecutionService`は待機と各操作の後で`ConfigureAwait(false)`を使用する。マクロ内の
ShortcutKeyは、その後`ShortcutKeyExecutionCoordinator`を通じて`MainWindow`の退出処理を
直接呼ぶ。この処理はAppWindow、Composition、DispatcherQueueTimer等へ触れるため、
UIスレッドで実行する必要がある。

レビュー用検証では、「Wait→ShortcutKey」に相当する経路で、マクロ開始スレッドと
ウィンドウ準備コールバックの実行スレッドが異なることを確認した。ランチャー表示中は、
スレッド違反、退出失敗、キー送信失敗につながる可能性がある。

対象:

- `Windows_SC.Core/Application/MacroExecutionService.cs`
- `Windows_SC.Core/Application/ShortcutKeyExecutionCoordinator.cs`
- `Windows_SC/MainWindow.xaml.cs`の`PrepareShortcutKeyTargetAsync`

改善案:

1. `ShortcutKeyExecutionCoordinator`のUI準備要求を`IUiDispatcher`経由にする。
2. Dispatcherへの投入失敗、ウィンドウ終了中、退出タイムアウトを明示的な失敗結果にする。
3. 通常ボタンと「Wait→ShortcutKey」の両経路で、同じUIスレッド保証をテストする。
4. GUIで、表示中のランチャーが退出した後に直前のアプリへキーが届くことを確認する。

参考: [Microsoft: Keep the UI thread responsive](https://learn.microsoft.com/en-us/windows/apps/develop/performance/keep-ui-thread-responsive)

### P1-03 一部の破損JSONが復旧処理から漏れ、起動不能が継続する

分類: バグ、堅牢性、データ保護

確認状態: 再現済み

設定JSONのルートが配列の場合や、`SchemaVersion`が文字列または真偽値の場合、
`LauncherSettingsMigrator`から`InvalidOperationException`が発生する。現在の
`JsonSettingsRepository.LoadAsync`はこの例外を復旧対象としていないため、破損ファイルの退避と
既定設定の生成へ進まない。アプリ音量状態でも`Entries`内に`null`があると
`NullReferenceException`が発生し、隔離処理から漏れる。

影響:

- 設定ファイルが残るため、再起動しても同じ失敗が続く。
- 起動時の同期ロードから例外が漏れ、アプリが利用できなくなる可能性がある。
- 「破損設定を退避して既定値へ復旧する」という現行設計と一致しない。

対象:

- `Windows_SC.Core/Application/LauncherSettingsMigrator.cs`
- `Windows_SC/Services/JsonSettingsRepository.cs`
- `Windows_SC.Core/Application/ApplicationVolumeStateStore.cs`
- `Windows_SC/App.xaml.cs`の起動時ロード

改善案:

1. JSONルートがオブジェクトであることを移行前に検証する。
2. `SchemaVersion`の型を安全に読み、型不一致を設定不正として扱う。
3. 配列内の`null`要素を拒否または読み飛ばす。
4. 構造不正、型不正、null要素、将来版、I/O失敗を別々にテストする。
5. 復旧処理自身が失敗した場合は、元ファイルを失わず利用者へ起動エラーを示す。

### P2-01 アプリ別音量状態の保存が並行実行される

分類: バグ、データ保護、並行処理

確認状態: 再現済み

`ApplicationVolumeStateStore.SaveSnapshot`は辞書のスナップショット取得だけをロックし、
共通の`.tmp`ファイルへの書込みと置換はロック外で行う。デバウンスタイマー、明示的な
`FlushAsync`、終了時`Dispose`が重なると、複数処理が同じ一時ファイルを操作する。

レビュー用の並列Flush検証では、100回中91～95回が`IOException`になった。

改善案:

- スナップショット作成から置換完了までを単一の保存ゲートで直列化する。
- タイマー保存と終了時保存に同じゲートを使用する。
- 終了時は進行中の保存完了を待ってからタイマーを破棄する。
- 並行Set／Flush／Disposeの回帰テストを追加する。

### P2-02 設定保存の所有期間が設定ウィンドウの寿命に限定される

分類: 設計、データ保護、保守性

確認状態: 静的解析

`SettingsPersistenceCoordinator`は`SettingsViewModel`ごとに生成される。設定保存中に
ウィンドウを閉じて再表示すると、新しいViewModelと新しい保存ゲートが作られるため、旧画面の
保存またはロールバックと新画面の保存を直列化できない。アプリ終了も進行中の保存完了を待たない。

改善案:

- 保存調整器をアプリ単位のサービスとして所有する。
- 設定ウィンドウを閉じる場合の取消しまたは完了待ちを定義する。
- アプリ終了は保存中状態を確認し、安全に完了または中止してからサービスを破棄する。
- 「保存中に閉じる→再表示→再保存」「保存中に終了」をGUIで確認する。

### P2-03 UI Automationの失敗がWin32代替検出も妨げる

分類: バグ候補、可用性、設計

確認状態: 静的解析

`UiAutomationStartMenuInspector.ScanDesktopAutomationTree`は、フォーカス要素のUI Automation調査を
実行してからWin32のウィンドウ判定へ進む。UI Automation側で例外が発生すると外側のcatchが
Snapshotを非表示へ更新し、その回のWin32判定は実行されない。UI Automationプロバイダーが
長時間停止した場合も、同じスキャンワーカー上の代替処理は待たされる。

改善案:

- UI Automation調査を局所的にcatchし、失敗後もWin32判定を実行する。
- UI AutomationとWin32候補取得の結果を分離してから統合する。
- 遅いプロバイダー、要素消滅、COM例外時にWin32経路が残ることを確認する。

### P2-04 通常ログに未処理例外メッセージが記録される

分類: プライバシー、セキュリティ、仕様不一致

確認状態: コードと匿名化処理を確認済み

`App.WriteUnhandledException`は未処理例外のメッセージを`WriteCritical`で通常ログへ記録する。
匿名化は既知のユーザーパスを中心とするため、別ドライブの実パス、URI、コマンド断片、トークン等の
任意文字列を除去できない。レビュー用検証でも、既知ルート外のパスと任意トークンは残った。

改善案:

- 通常ログは発生元、終了予定、例外型、HRESULTだけにする。
- 例外メッセージは詳細ログだけへ書く。
- `WriteCritical`にも通常用と詳細用の別メッセージを渡せるAPIを用意する。
- 通常ログへ実パス、コマンド、デバイス名、例外メッセージが入らない回帰テストを追加する。

### P2-05 ShortcutKeyの送信先を送信直前に確認していない

分類: セキュリティ、誤操作防止、信頼性

確認状態: 静的解析

ShortcutKey実行時はランチャーの退出完了を待った後、75ms待機して`SendInput`を呼ぶ。
直前にフォーカスしていたウィンドウの保持や、送信直前の前面ウィンドウとの照合は行っていない。
待機中に通知や別アプリが前面へ出ると、想定外の相手へキーを送る可能性がある。

改善案:

- 操作開始時に対象となる前面ウィンドウを保存する。
- 送信直前に前面ウィンドウを照合し、不一致なら中止して利用者へ示す。
- 既に物理的に押されている修飾キーがある場合の動作を定義する。
- 管理者権限アプリ等、UIPIにより送信できない場合を明確な失敗として扱う。

参考: [Microsoft: SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

### P2-06 音声出力切替の同期処理がUIとWindowsキーフックを停止させる可能性がある

分類: パフォーマンス、可用性、スレッド設計

確認状態: 静的解析

`WindowsAudioOutputService.CycleAsync`は`Task`を返すが、デバイス列挙と既定出力切替を
呼び出し元スレッドで同期実行する。列挙内部には非同期APIの同期待機もある。通常のボタン操作では
UIスレッドから呼ばれ、同じスレッドには`WH_KEYBOARD_LL`フックも登録されているため、
音声デバイスやCOM応答の遅延がUI停止とWindowsキー監視の停止につながる可能性がある。

改善案:

- 音声出力の列挙、切替、通知の再設定を専用MTAキューで直列化する。
- UIへは不変のスナップショットだけを通知する。
- 遅延、デバイス切断、連打、終了競合を確認する。

Microsoftは低レベルキーボードフックを短時間で返す必要があり、タイムアウト時には通知なく
解除され得るとしている。

参考: [Microsoft: LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)

### P2-07 常駐中のログサイズと待機キューに上限がない

分類: パフォーマンス、ディスク使用量、長時間安定性

確認状態: 現行仕様として確認済み

通常ログと詳細ログの2MBローテーションは起動時だけ行われる。長時間常駐や詳細ログの
常時有効モードでは、次回起動までファイルが増え続ける。また、書込み失敗や遅いストレージの際に
`ConcurrentQueue`へ蓄積する件数にも上限がない。

改善案:

- 書込み時にもサイズを確認し、ファイルゲート内で安全にローテーションする。
- 通常／詳細ログごとの最大保持容量と世代数を定める。
- キュー上限またはバッチ上限を設け、超過時の集約ログを残す。
- 詳細ログ常時有効での長時間試験を行う。

### P2-08 配布生成失敗時に以前の成果物を失う

分類: 配布設計、保守性

確認状態: 静的解析

`Build-Distribution.ps1`はpublish開始前に`artifacts/distribution`全体を削除する。
publishや圧縮に失敗すると、直前まで存在した検証済みZIPも失われる。また、同一版番号のZIPを
内容だけ差し替える操作をスクリプト側では防止していない。

改善案:

- 実行ごとの一時ディレクトリへ生成し、検証成功後に成果物を配置する。
- 同じ版番号のZIPが存在する場合は既定で失敗させる。
- ZIP内のEXE数、版情報、README、ファイル一覧、SHA-256を配置前に検査する。
- 失敗時にも以前の成果物を残す。

### P3-01 大規模ViewModelとMainWindowの責務分割を継続する

分類: 保守性、テスト容易性

確認状態: 構造確認

レビュー時点で`SettingsViewModel.cs`は1,617行、`MainWindow.xaml.cs`は1,169行である。
既存のCore分離により設定検証や非同期調整はテスト可能になったが、保存の所有期間、
UIスレッドへの切替、ウィンドウ終了との連携はWinUI側に残っている。

行数削減だけを目的にせず、次の境界で段階的に分ける。

1. アプリ全体の設定保存トランザクションと終了調整。
2. ShortcutKey送信前のUI退出と対象ウィンドウ検証。
3. 設定画面のButton、Cycle、Volume、Monitorエディター。
4. MainWindowの表示状態、入力イベント、復帰処理、エラーダイアログ。

`UI_MVVM_REFACTORING_PLAN.md`のPhase 5、6、9と統合し、P1、P2の修正単位を越える
全面的な再構成は避ける。

### P3-02 テスト範囲を実行時境界へ広げる

分類: 品質保証、保守性

確認状態: 現行72件の範囲を確認

Coreテストは設定モデル、移行、検証、マクロの順序、最新値処理等をよく確認している。
今回の問題は、実ファイル、cmd.exe、WinUI Dispatcher、終了処理、COMを跨ぐ境界に集中している。

追加を推奨するテスト:

- 一時ディレクトリを使う設定破損・退避・復旧テスト。
- 実際のcmd.exeを使うCommand／BatchFile統合テスト。
- UI Dispatcherを抽象化したShortcutKey準備のスレッドテスト。
- アプリ音量状態の並行Set／Flush／Disposeテスト。
- 保存中の設定画面クローズとアプリ終了の手動試験。
- 長時間ログ、音声デバイス遅延、UI Automation停止を想定した耐久試験。

## 4. 推奨する実施順

複数領域を同時に大きく変更せず、次の単位で進める。

1. Command／BatchFileの引用処理を修正し、実プロセス統合テストを追加する。
2. ShortcutKeyのUI Dispatcher境界を修正し、「Wait→ShortcutKey」を確認する。
3. 設定と音量状態の破損入力を安全に隔離し、ファイルベースのテストを追加する。
4. アプリ音量状態の保存を直列化する。
5. 設定保存サービスの所有期間と終了処理を整理する。
6. UI Automation失敗時もWin32代替経路を維持する。
7. 通常ログから例外メッセージを除き、ログの実行時ローテーションを追加する。
8. 音声出力処理を専用キューへ移し、長時間・実デバイス試験を行う。
9. 配布スクリプトを失敗時に既存成果物を保持する方式へ変更する。
10. 残るUI・MVVM分割と文書整理を行う。

各変更では、スタート検出、Composition表示状態、Core Audio COM制御を一度に
作り替えない。関連する自動テストとDebug／Release x64ビルドを実行し、GUI確認が必要な項目は
`TEST_CHECKLIST.md`へ記録する。
