# UI・MVVMリファクタリング計画

作成日: 2026-08-09
対象: Windows_SC `0.8.0`以降
状態: Phase 0完了・Phase 1～4実装中

## 1. 文書の目的

本書は、`0.8.0`の機能拡張後に増えたUI、ViewModel、非同期処理の保守リスクを、
既存動作を維持しながら段階的に解消するための現行実装計画である。

最初に再現条件のある不具合候補を修正し、その後に責務分割、XAML整理、テスト境界の
改善を行う。後半PhaseではUI非依存コードを`Windows_SC.Core`へ分離し、製品コードを
CoreとWinUI本体の2プロジェクト構成へ移行する。ファイル行数やプロジェクト内のファイル数を
減らすことだけを目的にせず、次の状態を目標とする。

- 保存中の編集や複数の保存経路で設定を失わない。
- スライダーやキー記録等の連続入力が、非同期処理中も最終操作どおりに確定する。
- ViewModelの状態遷移をWinUIウィンドウなしで検証できる。
- XAMLバインディングの誤りを可能な範囲でビルド時に検出できる。
- スタート検出、表示モーション、音声COM制御の回帰範囲を必要以上に広げない。

## 2. 文書のライフサイクル

本書は、対象作業のコード実装と必要なGUI確認が完了するまで`docs`直下で進捗を管理する。
各Phaseについて、未着手、実装中、コード完了、手動確認完了を区別して記録する。

全Phaseの完了後は、最終結果、主要コミット、採用しなかった案、残存リスクを追記し、
`docs/archive/UI_MVVM_REFACTORING_PLAN_YYYY-MM-DD.md`へ移す。恒久的な仕様と変更時の
注意は`DESIGN.md`、各メンテナンス文書、`TEST_CHECKLIST.md`へ反映し、本書を保守仕様として
残さない。

## 4. 維持する不変条件

### 4.1 設定

- 設定は明示的な保存操作で確定し、自動保存へ変更しない。
- 保存前検証、失敗項目と操作の再選択、保存失敗時の既存設定保護を維持する。
- JSON保存、自動起動反映、失敗時ロールバック、ランチャー反映の順序を根拠なく変えない。
- 保存前の編集コピーを`MainWindowViewModel`や終了時保存へ混入させない。

### 4.2 操作と音声

- `Application`、`File`、`URL`は保存モデル上で`Command`と別の操作種別として維持する。
- 音声出力循環は登録順の2台以上をデバイスIDで管理し、次の出力先を表示する。
- アプリ別音量は出力デバイスIDとアプリ識別子の組み合わせを維持する。
- キー入力はボタンまたはマクロ実行時だけ送信し、グローバルホットキー機能へ変更しない。

### 4.3 スタート連動と表示

- Windowsキー経路とスタートボタン経路の両方を維持する。
- UI Automation通知だけを唯一の検出手段にしない。
- スタート検出、Composition表示状態、COM音声制御を同じ変更で大きく作り替えない。

## 5. 優先して修正する不具合候補

### B-01 保存開始後の編集が保存済み扱いになる

現状は、`SaveAsync`が編集内容から設定を生成して非同期保存した後、保存中に追加の編集が
行われたかを確認せず`MarkSaved`を呼ぶ。保存開始後に入力した内容がファイルへ含まれなくても、
未保存表示が解除される可能性がある。

対応方針:

- 編集リビジョンを導入し、保存開始時と完了時が一致した場合だけ未保存状態を解除する。
- 保存中に追加変更があれば、保存済みスナップショットをランチャーへ反映した上で、
  編集画面は未保存状態を維持する。
- 保存、詳細診断設定、終了時保存の競合を同じ保存調整境界で管理する。
- 保存中の終了や設定画面クローズに対する方針を明示し、処理中Taskを放置しない。

完了条件:

- 保存中に編集する自動テストで、追加編集が未保存として残る。
- 一般保存と詳細診断設定を並行要求しても、古い設定全体で上書きされない。
- 自動起動反映失敗時の既存ロールバックと利用者向け表示が維持される。

### B-02 音量スライダーの連続入力が失われる

現状のアプリ別音量は、1回の設定処理中に届いた後続値を破棄する。マスター音量はCOM操作を
UIスレッドから同期的に呼ぶため、連続操作時の応答低下要因になる。

対応方針:

- 最新値優先のcoalescingまたは短いdebounceを導入する。
- 処理中に値が変わった場合は最後の値を保持し、処理完了後に必ず適用する。
- マスター音量とアプリ別音量のUI側実行モデルを揃える。
- 操作中の古い状態通知でSlider表示を巻き戻さない。

完了条件:

- 連続した複数値を入力する自動テストで、最後の値がサービスへ渡る。
- GUIでドラッグとホイール操作を行い、表示値と実音量が一致する。
- 外部音量変更、対象アプリ終了、デバイス切替後も状態更新が停止しない。

### B-03 キー記録対象の変更・削除で入力抑止が残る

現状はキー記録開始時の項目IDまたはマクロステップIDを保持するが、選択変更や対象削除時に
記録を終了しない。対象が見つからない完了経路では入力抑止解除まで到達しない。

対応方針:

- 記録開始、完了、キャンセル、対象消失、画面終了を専用の記録セッションで管理する。
- 選択変更、実行種類変更、対象削除では記録をキャンセルする。
- すべての失敗経路で物理キー抑止と固定ホットキー抑止を解除する。

完了条件:

- 記録中に項目またはステップを削除しても、入力抑止が必ず解除される。
- 記録中に別項目へ移動しても、以前の対象へ意図せず保存されない。
- Esc、設定画面クローズ、アプリ終了の各経路を確認する。

### B-04 UIオブジェクトと通知の寿命が不明確

現状はホイール差分用の辞書が`Slider`を強参照し、項目再構築後の古いコントロールを保持する
可能性がある。またエラーダイアログ表示中に届いた2件目以降の失敗は表示されない。

対応方針:

- Slider単位の一時状態を弱参照、`Unloaded`解除、またはViewModel側の値状態へ移す。
- 操作失敗をキュー化するか、ランチャー全体の実行調整で同時失敗を制御する。
- 項目再構築中の実行完了通知を破棄するか引き継ぐかを仕様として決める。

### Phase 5: 設定UIとViewModelの分割

最初は既存のXAMLバインディング名と保存順序を維持し、責務だけを移す。

推奨構成:

```text
Services/
├─ SettingsPersistenceCoordinator.cs    # 保存、反映、ロールバック、リビジョン
└─ ShortcutRecordingSession.cs          # キー記録と入力抑止の寿命
ViewModels/Settings/
├─ SettingsViewModel.cs                 # 画面全体の合成と選択
├─ AudioDeviceSettingsViewModel.cs      # 出力候補と登録順
├─ ApplicationVolumeSettingsViewModel.cs# アプリ候補と選択
└─ DiagnosticsSettingsViewModel.cs      # 詳細診断と環境情報
Views/
└─ Settings/
   ├─ ButtonEditor.xaml
   ├─ CycleEditor.xaml
   ├─ VolumeEditor.xaml
   ├─ MonitorEditor.xaml
   └─ DiagnosticsPanel.xaml
```

XAML分割時は次を守る。

- DataTemplateと分割Viewへ`x:DataType`を指定し、可能な箇所を`x:Bind`へ移行する。
- Picker、ContentDialog、ウィンドウサイズ・DPI処理はView側に残す。
- 項目未選択、操作未選択時の空状態を明示し、保存されない入力欄を操作可能にしない。
- 上下移動と削除はパラメーター付きCommandへ統一し、端では無効化する。
- 記号ボタンへ明示的な`AutomationProperties.Name`を付ける。

### Phase 6: ランチャー側の整理

`LauncherItemViewModel`は、永続化モデルを変えずに次の状態を内部構成要素へ分離する。

- ボタン／マクロ実行状態
- 循環切り替え状態
- 音量表示・設定状態
- システムモニター表示履歴

標準・コンパクトで重複するXAMLは、種類別DataTemplateまたはVisualStateで整理する。
表示結果を変える再設計とは分け、先に現在のサイズ、折返し、スクロール、表示件数を記録する。

`MainWindow.xaml.cs`は、スタート連動とモーションの状態遷移をサービスへ再分割しない。
必要な場合だけpartialファイルへ機械的に分類し、フィールド、タイマー、イベント購読順、
表示・退出条件を維持する。

### Phase 7: 2プロジェクト化に向けた依存境界の準備

物理的なプロジェクト移動より先に依存方向を整理する。このPhaseではファイルの所属を
大きく変えず、Coreへ移せるコードからWinUI型とWindows固有実装への参照を除く。

- 同期Action専用`RelayCommand`に加え、再入管理付き`AsyncRelayCommand`と
  `RelayCommand<T>`を用意する。
- ViewModelが直接取得している`DispatcherQueue`は、テスト可能な小さいUIディスパッチ境界へ置換する。
- `Visibility`、`InfoBarSeverity`、`PointCollection`などのWinUI型を、Core候補の状態や通知契約へ持ち込まない。
- 設定保存、音量最新値、キー記録の各調整クラスは、WinUIコントロールやWindowsサービスを
  直接参照せず、インターフェースから操作できる状態にする。
- `StateChanged`の直後に共有可変状態を再取得する方式を避け、必要な通知では不変スナップショットを渡す。
- Coreへ移す候補とWinUI本体へ残す対象を依存関係で分類し、単なる名前やフォルダーの印象で決めない。

Coreへ移す主な候補:

- 設定モデル、保存用スナップショット、移行、検証
- 操作・マクロのUI非依存契約と実行調整
- ショートカットキーの表現、解析、検証、入力シーケンス生成
- 音量設定の最新値調整など、COMを直接呼ばない状態管理
- ログ値のマスキングなど、Windows APIを必要としない処理

WinUI本体へ残す主な対象:

- View、ViewModel、WinUI用Commandアダプター、UIディスパッチ実装
- スタート検出、UI Automation、ウィンドウ、Composition、トレイ
- Core Audio COM、レジストリ、自動起動、Windows入力送信
- アプリ起動時のサービス生成、イベント接続、終了時の破棄

### Phase 8: Windows_SC.Coreの作成とProjectReferenceへの移行

製品コードは次の2プロジェクトを目標とする。`Windows_SC.Tests`を含めると、ソリューションは
3プロジェクトになる。下記のフォルダー名は責務を示す例であり、空の層や委譲だけの型は作らない。

```text
Windows_SC.Core/                         # UI、WinUI、Windows APIに依存しない
├─ Models/
├─ Application/                          # 保存、実行、音量、キー記録の調整
└─ Contracts/                            # 外部機能へ向けた小さいインターフェース

Windows_SC/                              # WinUIアプリとWindows固有実装
├─ AppHost/                              # 生成、接続、開始、停止、破棄
├─ ViewModels/
├─ Views/
└─ Services/Windows/

Windows_SC.Tests/
└─ ProjectReference -> Windows_SC.Core
```

依存規則:

- `Windows_SC`から`Windows_SC.Core`への一方向参照にする。CoreからWinUI本体を参照しない。
- CoreはWinUIおよびWindows App SDKパッケージを参照しない。可能な限り`net8.0`を対象にする。
- Windows固有サービスはCoreの契約を実装し、具象型をCoreのモデルやユースケースへ公開しない。
- `Windows_SC.Tests`はCoreを`ProjectReference`し、Coreへ移した製品ソースの個別`Compile Include`を廃止する。
- ファイル移動と動作仕様変更を同じコミットへ混ぜない。候補群ごとに移動し、毎回ビルドとテストを行う。
- 名前空間の全面変更は必須とせず、レビュー可能な単位を優先する。

Phase 8の完了条件:

- 製品コードが`Windows_SC.Core`と`Windows_SC`の2プロジェクトでビルドされる。
- Coreのプロジェクト参照とパッケージ参照にWinUI本体またはWindows App SDKが含まれない。
- テストがCoreの実際の成果物を参照し、製品ソースの複製コンパイルに依存しない。
- Debug／Release x64ビルドと全自動テストが、移動前後で同じ動作基準を満たす。

### Phase 9: 構成ルート、不要コード、文書、配布確認の整理

- `AppHost`相当の構成ルートで、サービスの生成者、イベント接続者、開始・停止・破棄順を明確にする。
- Windowは自ら生成していないサービスを独断で破棄せず、所有者へ終了要求を返す。
- 参照されていないCommand、Visibility、表示文字列、状態フィールドを検索して削除する。
- .NETアナライザーとnullable警告を維持し、XAML実行時バインディング警告もGUI確認時に調べる。
- `DESIGN.md`、専門メンテナンス文書、`TEST_CHECKLIST.md`へ確定した依存規則と確認手順を反映する。
- プロジェクト参照や出力構成を変更するため、配布スクリプトで通常ZIPを生成し、内容とローカル起動を確認する。

## 7. 今回変更しない領域

次は再現可能な関連不具合がない限り、本計画の構造整理へ含めない。

- `HybridStartMenuMonitor`と`UiAutomationStartMenuInspector`の監視方式
- `StartMenuWindowInspector`の候補選択と複数モニター判定
- `LauncherMotionCoordinator`と`CompositionLauncherMotionService`の状態遷移
- `WindowsAudioOutputService`と`WindowsApplicationVolumeService`のCOM宣言・解放順の全面再設計
- 設定スキーマ、既存JSON名、操作種別の統廃合
- 製品コードの3プロジェクト以上への細分化、またはDIフレームワーク導入だけを目的とした変更
- MSIXまたは単一EXEの配布再採用

音量スライダー修正でCOM呼出スレッドを調整する場合も、列挙、通知登録、既定出力切替、解放順を
同じ変更で再設計しない。

- 保存リビジョン、保存経路競合、音量最新値、キー記録解除を単体テスト化する。
- Debug／Release x64を`--no-restore`でビルドし、警告0・エラー0を確認する。
- Phase 8以後はCore単体とソリューション全体の参照が一方向であり、テストが
  `ProjectReference`経由で実際のCore成果物を検証していることを確認する。
- 文書リンクと`git diff --check`を確認する。

### GUI手動確認

- 設定保存中の追加入力、保存直後の設定画面クローズ、アプリ終了
- 保存失敗、自動起動反映失敗、既存設定へのロールバック
- マスター音量とアプリ別音量のドラッグ、ホイール、外部変更
- キー記録中の選択変更、削除、Esc、設定画面クローズ
- 項目なし、ステップなし、候補なしの空状態
- 上下移動ボタンの有効状態、キーボード操作、スクリーンリーダー名
- 標準／コンパクト、100%／125%以上のDPI、複数モニター
- Phase 8以後のアプリ起動、設定画面の表示・保存、代表的な各操作種別の実行

スタート検出またはMainWindow表示コードへ触れた場合は、Windowsキー、スタートボタン、
仮想デスクトップ、途中反転を追加確認する。ビルド成功だけでGUI確認済みとはしない。

Phase 8以後はプロジェクト構成と出力を変更するため、`Build-Distribution.ps1`で通常ZIPを
生成し、必要ファイル、ローカル展開、起動を確認する。別PC確認とGitHub Release公開確認は
別作業として扱い、実施していない場合は未確認と記録する。
