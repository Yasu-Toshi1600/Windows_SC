## 2. 製品概要

Windows 11のスタートメニューと同時に呼び出せる、常駐型の軽量ランチャーを提供する。
アプリ、ファイル、フォルダー、URL、コマンド、キー入力、マクロ、音声出力先、
マスター／アプリ別音量を操作し、システム使用率を表示できる。

主な利用者は本人と知人を想定し、一般公開サービス、企業向け集中管理、設定のオンライン同期は対象外とする。

## 3. 対応範囲

### 対応対象

- Windows 11 バージョン25H2以降
- x64
- 日本語環境
- 下端タスクバー
- タスクバーの中央揃え／左揃え
- 1080p以上を推奨。1080p未満は未検証であり、起動時の警告対象
- 複数モニター、異なるDPI、負座標を含む構成

製品として配布・判定するのはx64自己完結版だけとする。プロジェクトに残るx86／ARM64定義は製品サポートを意味しない。

### 対象外

- Windows 10、Windows 11 24H2以前
- x86、ARM64の配布保証
- 上、左、右に配置したタスクバー
- 1080p未満向けの表示保証と専用レイアウト。解像度自体は起動時の強制終了条件にしない
- Microsoft Store公開、自動更新、クラウド同期
- 複数ページUI、項目を階層化するフォルダー、プラグイン、Windowsウィジェットボード統合
- コマンドの終了待機、終了コード、タイムアウト、標準出力取得

起動時にOSビルド、OS／プロセスアーキテクチャ、タスクバー位置、接続中ディスプレイの解像度を検査する。Windows 11 25H2（ビルド26200）未満、x64以外、下端以外のタスクバー、またはタスクバー位置を確認できない環境では、理由と対応環境をエラーダイアログで表示してアプリを自動終了する。接続中のいずれかのディスプレイで縦横の短い方が1080ピクセル未満の場合は、未検証であることを警告し、利用者の確認後に起動を続ける。日本語環境と解像度は起動時の強制終了条件に含めない。

## 4. アプリのライフサイクル

### 起動

1. 保存場所と通常ログを初期化し、単一インスタンスを取得する。既に起動中なら2個目は常駐せず終了する。
2. 対応環境を検査し、非対応ならエラーダイアログを表示して終了する。1080p未満のディスプレイが接続されていれば警告を表示し、確認後に処理を続ける。
3. 設定を読み、旧版は現行スキーマへ移行し、破損データは退避して既定設定へ復旧する。将来版の設定は変更せず、警告を表示して終了する。
4. ランチャーウィンドウ、入力監視、スタート監視、音声サービス、通知領域アイコンを初期化する。
5. ランチャーと設定画面を表示せず、通知領域に常駐する。

UI Automationのイベント登録は外部プロバイダーで遅れる場合があるため、スキャン用スレッドと分離する。監視準備中でもトレイ、設定、終了、手動ホットキーを利用可能にする。
イベント登録が成功した後も、長時間稼働で通知が無言で途絶える場合に備え、
非表示・非対話中は250ms間隔の軽量なWin32可視確認を継続する。可視候補がある
場合だけUI Automationスキャンを要求する。

### 表示入口

- Windowsキー単体
- タスクバーのスタートボタンクリック
- `Ctrl+Alt+Space`
- 通知領域メニューの「ランチャーを表示」

Windowsキーを含む別ショートカットは単体入力として扱わない。`Ctrl+Alt+Space`は現行固定値であり、変更UIは初回版に含まれない。

### 終了

- 通知領域メニューの「終了」
- 設定画面の終了操作

終了時は設定保存の共通キューが空になるまで待ってから、入力フック、UI Automation監視、トレイアイコン、音声サービス、ログライター等を解除する。ランチャーを閉じる操作はアプリ終了ではなく、非表示常駐への復帰である。

ウィンドウ資源はAppが明示的に先に解放し、各サービス、単一起動制御、ロガーの順で終了する。
GPU計測の初期化・計測・解放は直列化し、ネイティブ解放はバックグラウンドで実行する。
終了側の解放待ちは最大1秒とし、未完了の場合もUIを無期限に待たせない。
調査結果と残る検証は[終了処理の調査記録](SHUTDOWN_INVESTIGATION_2026-09-06.md)を参照。

## 5. ランチャー画面

### ウィンドウ

- 枠、タイトルバー、リサイズ、最大化、最小化を持たない。
- タスクバーとAlt+Tabの一覧に表示しない。
- 表示中は常に手前に置く。
- 高さは現行600 physical pixelを基準とし、項目部分を縦スクロールする。
- スタート連動時は検出したスタートと同じモニターの右側へ配置する。
- 手動表示時はカーソルがあるモニターの作業領域中央へ配置する。
- スマートフォン連携パネルは設定値により予約幅を確保する。個別パネルのUI Automation走査は性能上無効である。

右側の幅が不足する場合は、標準またはコンパクトの列数を減らす。それでも最低幅を確保できない場合は表示を中止し、理由をログへ残す。

### レイアウト

- 標準: 通常ボタンを最大2列
- コンパクト: 通常ボタンを最大4列
- 循環切り替えと音量スライダー: 通常ボタン2列分
- 利用可能幅に応じて列数を減らす
- 表示するたびスクロール位置を先頭へ戻す

### 表示・非表示

- スタート連動表示ではランチャーをアクティブ化せず、スタート検索のフォーカスを奪わない。
- 表示要求時にランチャーが別の仮想デスクトップへ所属している場合は、現在操作中の仮想デスクトップへ移動し、古い表示状態を破棄してから配置・表示する。
- ランチャーへフォーカスまたはポインター操作が移ると対話状態になり、スタートが閉じても表示を維持する。
- Windowsキー、スタートの終了、外側クリック、Escape、設定表示、成功後に閉じる操作で退出する。
- 退出中の新しい表示要求は現在位置から進入へ反転する。

詳細な状態と時間はモーション仕様書、検出条件はスタート保守ガイドに従う。

## 6. ランチャー項目

### 共通

各項目はID、種類、表示名、配置順を持つ。現行の種類はボタン、循環切り替え、
音量スライダー、システムモニターである。

### ボタン

次のいずれかを起動する。

- アプリ、実行ファイル
- ファイル、フォルダー、URL、Windows URI
- コマンド、bat、cmd
- ShortcutKeyによるキー入力
- 複数操作と待機を登録順に実行するマクロ

設定画面では、Shell実行するApplication、File、URLを「アプリ・ファイル・URL」、
cmd経由で実行するCommand、BatchFileを「コマンド・bat」としてまとめ、キー入力、マクロと
合わせた4分類で表示する。既存設定との互換性のため保存モデルの列挙値は維持する。ShortcutKeyは
グローバルホットキーではなく、ボタン操作時だけ`SendInput`で送信する。ShortcutKeyごとに
ScanCode方式またはVirtualKey方式を選択し、入力配列を1回で一括送信する。送信先は送信時点の
前面ウィンドウであり、操作開始時のフォーカスへ固定しない。物理修飾キーの状態も補正しない。マクロは
最大50ステップ、1待機最大10秒、全体最大60秒とし、失敗時はそのステップで停止する。

設定可能な値:

- 起動対象またはコマンド
- 引数
- 作業フォルダー
- コマンド画面を非表示にするか。ただしコマンド／bat実行時だけ表示する。

起動対象と作業フォルダーでは環境変数を展開する。PATHやApp Pathsで解決できるEXEはフルパスなしで起動できるが、Storeアプリ等はURIや解決可能な対象を指定する。

ボタンは起動要求に成功したらランチャーを閉じる。「実行後」の選択欄は表示しない。失敗時はランチャーを残してエラーを表示する。

### 循環切り替え

2件以上を登録し、操作ごとに登録順で次へ進み、末尾の次は先頭へ戻る。

#### 音声出力

- 登録した既定出力デバイスを順番に切り替える。
- ランチャーには現在の既定出力ではなく、次に切り替わる利用可能な出力先を表示する。
- 切断、無効、利用不能なデバイスは飛ばす。
- 再接続後は再び候補へ戻す。
- 現在の既定デバイス以外に切り替え可能な候補がない場合は操作不能にする。
- 実行位置は現在の既定出力を基準に決め、永続化しない。

#### コマンド

- 表示名、対象、引数、作業フォルダー、画面表示方針をステップごとに持つ。
- 起動要求の成否にかかわらず、操作するたび登録順で次のステップへ進む。
- 起動要求に失敗した場合はランチャーを閉じず、エラーを表示する。
- アプリはプロセス終了と終了コードを追跡しないため、コマンド自身の失敗は判定しない。

循環切り替えは「成功後に閉じる」または「表示したまま」を設定でき、既定値は「成功後に閉じる」とする。
「表示したまま」で表示ありのコマンドを起動した場合、コマンド画面へのフォーカス移動ではランチャーを閉じない。ランチャーを再度アクティブ化した後は、通常どおり画面外クリックで閉じる。

### 音量スライダー

- マスター音量は現在の既定出力デバイス全体を操作する。
- 既定出力の音量・ミュート変更通知を購読し、ミュート中はマスター音量の数値表示を
  リアルタイムで「ミュート」へ切り替える。
- アプリ別音量は既定Render／Multimedia出力上の同一アプリの全セッションを操作する。
- アプリ別音量は出力デバイスIDと正規化したアプリ識別子の組み合わせで別ファイルへ保存する。
- 保存値がある出力先へ戻った場合だけ自動復元し、未保存の出力先は現在値を上書きしない。
- 既定デバイスが利用不能な場合は操作不能にする。
- 実行後動作は設定しない。

### システムモニター

- CPU、GPU、メモリから1つまたは2つを選択して1カードへ表示する。
- 2項目選択時は使用率だけを2行で表示する。1項目選択時は使用率と、ランチャーを開いている間の
  最大60秒の履歴グラフを表示する。
- ウィジェット高さは標準160 DIP、コンパクト80 DIPとする。コンパクトの1項目表示は
  タイトルと項目名を上段、グラフを下段へ配置し、2項目表示は使用率を横並びにする。
- GPUを取得できない環境と初回サンプルは`—`を表示し、0%と断定しない。
- ランチャー表示中だけ1秒間隔で取得し、非表示中は停止する。

## 7. 設定画面

単一の設定画面で、一般設定、項目一覧、選択中項目の編集、トラブルシューティングを提供する。

### 一般設定

- スマートフォン連携パネルの予約
- 標準／コンパクトレイアウト
- Windowsログオン時の自動起動

### 項目編集

- 追加、削除、上下移動
- 種類、表示名
- ボタンの実行種類と対象
- アプリ・ファイル・URLを開く場合のファイル／フォルダー選択
- 循環切り替えのモード、音声デバイスまたはコマンドステップ
- 循環切り替えの実行後動作

上下移動後も対象を選択したまま表示領域へ追従させる。選択中の実行種類を表示し、種類に応じて入力名、例、補助設定を切り替える。

### 保存

- 自動保存しない。
- 下部の「保存」で入力検証、JSON保存、自動起動反映、ランチャー再構築を行う。
- 保存前の変更をランチャーや終了時保存へ混入させない。
- 一般設定と診断設定の保存はアプリ単位の同じ保存調整器で直列化し、アプリ終了時は進行中および待機中の保存完了を待つ。
- 詳細診断ログだけはトラブルシューティング内の専用適用を使う。
- 全列挙値と種類ごとの必須データを読込時に検証し、不正な設定は破損バックアップへ退避する。
- 保存はJSONを先に確定してから自動起動を反映する。自動起動が失敗した場合は両方を保存前へ戻し、実際の自動起動状態を利用者へ表示する。

新規作成または破損復旧時の既定項目は、メモ帳、電卓、エクスプローラー、Windows設定とする。

## 8. 通知領域

起動中は`Windows_SC`アイコンを1個表示する。左クリック、右クリック、キーボード選択から同じメニューを開く。

- ランチャーを表示
- 設定
- 終了

「非表示」は設けない。メニュー操作でフォーカスが移り、必要な場合はランチャー側のlight-dismiss処理が働く。Explorer再起動後はタスクバー再生成通知を受け、アイコンを再登録する。

## 9. 現行アーキテクチャ

| 領域 | 主な実装 | 責務 |
|---|---|---|
| 起動と寿命 | `App.xaml.cs` | サービス生成、単一インスタンス、設定読込、トレイ、設定画面、終了 |
| ランチャーUI | `MainWindow.xaml(.cs)` | 表示入口、配置、状態同期、モーション開始、light-dismiss |
| ランチャー状態 | `MainWindowViewModel`、`LauncherItemViewModel` | 項目構築、実行、音声状態反映 |
| 設定UI | `SettingsWindow.xaml(.cs)`、`SettingsViewModel`、`DiagnosticsSettingsViewModel`、`DiagnosticsPanel` | 編集用コピー、保存前検証、該当項目の再選択、明示保存、診断操作 |
| スタート監視 | `HybridStartMenuMonitor`、`UiAutomationStartMenuInspector`、`StartMenuWindowInspector` | UIA／Win32検出、Snapshot、フォールバック |
| モーション | `LauncherMotionCoordinator`、`CompositionLauncherMotionService` | 論理状態、Translation、Opacity、反転、完了通知 |
| 配置 | `LauncherPlacementService` | モニター、DPI、作業領域、列数、ランチャー矩形 |
| 入力 | `GlobalInputService`、`GlobalWindowsKeyMonitor`、`WindowInteropService` | Windowsキー、ホットキー、外側クリック、Escape |
| アクション | `ActionExecutionService`、`ShortcutKeyExecutionService`、`MacroExecutionService` | Shell／cmd起動、キー送信、登録順実行 |
| 音声 | `WindowsAudioOutputService`、`WindowsApplicationVolumeService` | 既定出力切り替え、マスター音量、MTA上のセッション監視とアプリ別音量 |
| アプリ音量状態 | Coreの`ApplicationVolumeStateStore` | 出力先＋アプリ識別子の遅延作成、debounce、atomic保存 |
| システム指標 | `WindowsSystemMetricsService` | CPU／GPU／メモリ取得、表示中だけの定期更新 |
| 設定保存 | `JsonSettingsRepository`、Coreの`LauncherSettingsValidator`、`ApplicationDataPaths` | JSON、スキーマ検証、旧保存場所からの移行、破損バックアップ、保存先 |
| 診断 | `DiagnosticLogger`、Coreの`LogPrivacySanitizer`、`ApplicationInformation`、`EnvironmentInformationService` | 通常／詳細ログ、匿名化、環境情報の取得・変更検出 |
| OS統合 | `WindowsSystemTrayService`、`RegistryStartupService`、`SingleInstanceService` | トレイ、自動起動、二重起動防止 |

製品コードは`Windows_SC.Core`と`Windows_SC`の2プロジェクトで構成する。Coreは`net8.0`を対象とし、
WinUI、Windows App SDK、Windows APIを参照しない。WinUI本体とWindows固有サービスからCoreへの
一方向参照とし、テストも製品ソースのリンクではなくCore成果物を参照する。
Coreで確認する領域とWindows／GUI確認へ残す領域は`CORE_TESTING.md`を正とする。

Win32、COM、WPF UI Automation等のOS依存処理はサービス境界へ置き、ViewModelから直接呼ばないことを基本とする。例外的な現行コードを追加するときは、将来の分離方針を残件へ記録する。

## 10. 主なデータフロー

### スタート連動表示

```text
Windowsキー／スタートクリック
  → 入力・スタート監視
  → StartMenuSnapshot
  → MainWindowの状態同期
  → LauncherPlacementService
  → AppWindowを最終位置へ表示
  → Composition進入
```

### 項目実行

```text
項目操作
  → LauncherItemViewModel
  → ActionExecutionService または WindowsAudioOutputService
  → 成功／失敗
  → 循環位置・表示状態更新
  → 必要な場合だけランチャー退出
```

### 設定保存

```text
設定画面の編集コピー
  → 入力検証
  → JSON保存と自動起動反映
  → MainWindowViewModelへ適用
  → ランチャー項目再構築
```

```text
   ├─ window-diagnostics.detail.log
   ├─ window-diagnostics.detail.previous.log
   ├─ window-diagnostics.detail.previous.2.log
   └─ window-diagnostics.detail.previous.3.log
```

- 公開対象の非パッケージ版は、利用者から見える保存先を`%LOCALAPPDATA%\Windows_SC`へ統一する。旧MSIX版の保存場所は移行元として認識する。
- 自動起動は`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`へ現在の実行ファイルを登録し、登録・解除直後に同じ値を読み戻す。設定値、成功ログ、実レジストリ、次回ログオン起動を別々に確認する。
- 旧保存場所は初回読込時に新構成へ移行する。
- 設定はスキーマバージョンを持つJSONとする。
- 旧スキーマは読込時に現行版へ移行する。不正な設定は日時付きで退避し、退避できない場合も既定設定による初期化を試みる。
- 現行アプリより新しいスキーマは上書きせず、対応版の利用を促す警告を表示して終了する。
- ログキューは5000件を上限とし、連続する同一失敗を集約する。通常／詳細は各4ファイルを保持し、起動時のサイズ超過とスリープ／休止状態からの復帰時にローテーションする。
- 通常ログは常時有効とする。詳細ログは専用操作から24時間有効にする通常モードと、開発・継続調査用に手動解除まで継続する常時有効モードを持つ。
- アプリは設定とログを外部へ自動送信しない。
- 設定画面から開くフォルダーはデータルートだけとし、`Settings`と`Logs`はその配下で確認する。
- 環境情報は起動時に通常ログへ記録する。表示環境の変更通知は750ms待ってまとめ、前回記録した内容から変化した場合だけ再記録する。

UI Automation要素名は取得・記録しない。詳細ログにはコマンド、音声デバイス名、例外情報等が含まれる可能性があるため、共有前に利用者が確認する。トラブルシューティング画面にもこの注意を常時表示する。

## 12. エラー処理と安全性

- 対応環境検査の不一致は、短い日本語エラーダイアログと通常ログを残して起動を中止する。それ以外の予期可能な設定、音声、OS APIの失敗は可能な限りアプリ全体を終了させない。
- 設定破損では元ファイルを退避し、黙って上書きしない。
- アクション失敗ではランチャーを維持し、再操作可能にする。
- コマンド欄は`cmd.exe /d /s /c`で実行され、シェルメタ文字を解釈する。信頼できる利用者が入力する前提とし、外部から取得した設定を無確認で実行しない。
- 通常機能で管理者権限を要求しない。対象側が昇格を要求する場合はOSのUAC動作に従う。
- ログへ秘密値を意図的に記録しない。ただし詳細ログは完全匿名ではない。
- UIスレッド、AppDomain、未監視Taskの例外境界で、例外種別、HRESULT、終了有無を通常ログへ記録する。致命的例外は処理済みにせず、記録後も通常の異常終了動作に従う。

## 15. 設計変更時のルール

1. 現行動作を変更する場合は本書または該当する専門仕様を先に更新する。
2. スタート検出とモーションを変更する場合は、両文書の責務境界を保ち、片方だけに矛盾する状態遷移を追加しない。
3. 設定モデル変更ではスキーマ互換性、既定値、破損復旧、旧版移行を同時に検討する。
4. 新しいログ項目は通常／詳細の分類と個人情報リスクを確認する。
5. 利用者影響のある変更は`CHANGELOG.md`へ追記する。
6. 配布前はVersion、コミット、成果物、ログの版が一致することを確認する。
